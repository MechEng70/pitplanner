# Device tests

Unattended passes on the dev build (`io.github.mecheng70.pitplanner.debug`, "Pit Planner dev") over adb. The
default target is the test emulator (`avd.sh`: AVD `pitplanner`, Android 16 / API 36, Google APIs x86_64 on
KVM, 1080x2376 at 480 dpi = 360x792 dp like the phone, gesture navigation with its 24 dp bar; the display is
never resized), started headless when it is not running and stopped again. Jason's phone (`--phone`) is only for tests that need real hardware (TASKS "Real phone"). Maestro taps by accessibility label; `uiautomator dump` gives the bounds the checks compare;
screenshots are `adb exec-out screencap`, cropped below the status bar, never showing the keyboard (closed first,
or for `sheet-keyboard` cut at its top edge). Output goes to `out/` (git-ignored).

```
npm run device                                   # emulator: build + install, all tests at 115% and 130%
npm run device -- --phone --only smoke           # the real phone (only when a task needs it)
tools/device/avd.sh start | stop                 # the emulator by hand
npm run device -- --no-build --only sheet-keyboard
npm run device -- --only smoke,stable-controls
npm run device -- --no-build --only db --repeat 10   # a test that only sometimes fails
tools/device/avd.sh start; DEVICE_SCALES=1.15 tools/device/run.sh --no-build --only history   # one long test per call
AVD_API=34 tools/device/avd.sh start; AVD_API=34 DEVICE_SCALES=1.15 tools/device/run.sh --no-build --only alarm   # Android 14
```

Read `out/report.txt` first (the "device summary" block at the end), then the images it lists.

## Other Android versions (T-037)

`AVD_API=34` (Android 14) or `AVD_API=35` (Android 15) in front of `avd.sh` and `run.sh` uses that version's own
emulator, `pitplanner-api34` or `pitplanner-api35`: the same screen, its image downloaded on the first create
(about 4 GB each on disk). One emulator runs at a time: stop one before starting another, with the same
`AVD_API`. A new emulator has no dev build: install it once (`adb install -r
android/app/build/outputs/apk/debug/app-debug.apk`, or a run without `--no-build`). The first test run on a
new emulator fails once: the dev build opens its developer menu on its first launch. Run it again.

## Upgrade from 0.2.0 (emulator only)

`tools/device/upgrade020.sh setup` installs the real `release/pitplanner-0.2.0.apk` on the test emulator and
makes data through the app's own screens (`webview.mjs` drives its WebView over DevTools): Setup, a saved
brisket rate, a plan draft, two cooks saved to history. `upgrade020.sh check <apk>` installs a 0.3.0 build over
it and checks what the import moved (reads the SQLite database as root). It uninstalls and deletes nothing.

Upgrade with a live cook (T-016, T-038): after `setup`, `upgrade020.sh live` starts a short cook in 0.2.0
(wings, the smoker fired at the next 5-minute mark at least 7 minutes out) and leaves it running;
`upgrade020.sh alarms` lists the release app's pending alarms in AlarmManager beside its own stored set, before
and after `adb install -r` of the new build. The steps and what to look for are in `docs/alarm-testing.md`.

## Locked reboot (its own emulator, a release APK)

`tools/device/locked-reboot.sh <release apk>` (T-072; required before every release, `docs/RELEASING.md`
section 5b) checks that after a restart, while the device is still locked, a release build has its cook's
alarms registered again and a step that comes due rings. It uses a second emulator, `pitplanner-lock`
(`AVD_LOCK=1 tools/device/avd.sh start`; PIN `LOCK_PIN` in `lib.sh`), drives the app, the Files app and the
lock screen with `uiautomator` and `input` alone, and writes `out/locked-reboot.txt`. It is the only tool
here that clears an app's data: Pit Planner's, on `pitplanner-lock` only, at the start of each run (Jason's
limit; the script checks the target before it clears). `adb reboot` ends a headless emulator, so the script
restarts it with `avd.sh stop` and `start`. A dev build fails this test by design (see RELEASING).

## Safety

The phone is Jason's own. With `--phone`, `run.sh` wakes it and stops if it is locked; backs up the dev build's data
(`db.sh backup`, `out/data-<time>.tar`, the two newest kept) and restores it on exit; turns heads-up banners off and keeps the
screen on while plugged in; restores font scale and settings on exit. It never touches the release app.
A dump of any window that is not the app (the notification shade, another app) is refused: the shade is
collapsed, the step fails and nothing is written. Maestro's own output includes the phone's whole logcat
(other apps' logs, which can hold their tokens), so each Maestro call writes it to a temp dir that is deleted
right after; it never lands in `out/` or `~/.maestro/tests`. The device log is cleared (`adb logcat -c`)
before and after every run and saved only when a test fails: the app's own lines (by its uid), redacted for
token patterns (`redact.mjs`), to `out/logcat-failed.txt`.

## Pieces

| File | Role |
|---|---|
| `run.sh` | The pass: options, safety, build, Metro, tests, summary. |
| `lib.sh` | adb wrapper, cold launch through the dev-client link, `dump`, `tap`, `scroll_to`, status bar and keyboard edges. |
| `db.sh` | `backup [file]` / `restore <file>` of the app's data dirs over `run-as`. |
| `avd.sh` | Create, start (headless) and stop the test emulator. |
| `redact.mjs` | Token redaction for the failure log (tested in `redact.test.mjs`). |
| `check.mjs`, `ui.mjs` | Checks over dumps (`find`, `stable`, `keyboard`); pure logic tested in `ui.test.mjs` (`npm run test:gate`). |
| `targets.tsv` | `stable-controls` steps: target, route, start, expect, label, times (tab separated). |
| `crop.py`, `compose.py` | Crop the status bar; put screenshots side by side. |

Memory: the APK is built before the emulator boots, and the Gradle and Kotlin daemons are stopped in between
(`tools/stop-gradle.sh`); the emulator always runs with 3 GB (`avd.sh`). Limits for the daemons themselves are
in `plugins/gradleMemory.ts`.

Notes: Metro is started when it is not running. `launch` closes the dev menu's first-launch intro, and both
`launch` and every screenshot wait for the dev build's "Refreshing..." banner to clear. A cold start with a plain deep link opens the dev launcher, so
`launch` loads the bundle through `pitplanner://expo-development-client/?url=...` and then opens the route.
Maestro reads stdin, so it always gets `/dev/null`. Use bash, not zsh one-liners (zsh does not word-split).
Alarm device tests: `docs/alarm-testing.md` (re-run on the Expo build in T-016).
